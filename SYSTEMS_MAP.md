# Systems map

Where things live in Log Cabin and what changes together. Areas follow the product's
modules: the core every module builds on, then one area per module as it lands.

## Layout

```
log-cabin/
├── wrangler.jsonc          # the one Worker: bindings, crons, staging, beta and test envs
├── migrations/             # hand-written D1 SQL; numbers are reserved ahead, one per planned change
│                           # (0002–0026 so far), so a module may own several (calls: 0009, 0011);
│                           # a second file within one change is 00NN_b_<name>.sql
├── script/deploy           # provisions D1/R2/queue, migrates, sets secrets, deploys
├── script/rollback         # puts an earlier Worker version back on staging or beta (code only)
├── script/restore          # loads a beta backup into a database of its own
├── script/backup/          # the beta database's backup Worker; script/backup-deploy ships it
├── script/reindex          # rebuilds the search index from the tables
├── src/
│   ├── worker.ts           # Worker entry: SvelteKit fetch + queue() + scheduled() + RealtimeHub,
│   │                       # RecordingSink and the /calls/<id>/rec-sink route
│   ├── hooks.server.ts     # first-run redirect, session → locals
│   ├── lib/
│   │   ├── server/         # server-only code: db, auth, email, jobs, realtime, storage
│   │   ├── strings/        # every user-facing string, one file per module
│   │   ├── components/     # ui/ primitives (Storybook), shell/ app layout
│   │   └── nav.ts          # sidebar registry modules append to
│   └── routes/             # pages, one folder per URL
├── tests/e2e/              # Playwright tests: browsers against `wrangler dev` on the built Worker
├── playwright.config.ts    # starts `wrangler dev` for tests/e2e
├── .svelte-kit/            # generated (gitignored); cloudflare/_worker.js is SvelteKit's handler
└── .wrangler/              # local dev state (gitignored)
```

## Areas

### Worker runtime

For: One deployable Worker that serves pages, consumes background jobs, runs crons and hosts realtime rooms.
Lives at: `src/worker.ts`, `wrangler.jsonc`, `src/lib/server/platform.ts`, `vite.config.ts`
Why this shape: adapter-cloudflare writes its handler to whatever `main` it reads, so `vite.config.ts` gives it a generated config pointing at `.svelte-kit/cloudflare/_worker.js`, and `wrangler.jsonc` aliases that file as `sveltekit-worker` for `src/worker.ts` to wrap.
Seams: New queue consumers go in `handlers` and crons in `crons` (`src/lib/server/jobs/index.ts`); new Durable Object classes are exported from `src/worker.ts` and declared in `wrangler.jsonc`.
Fragile: Bindings reach app code only through `getEnv()` (`cloudflare:workers`); `event.platform` is undefined under this adapter. Files imported by `src/worker.ts` must use relative imports, since wrangler's bundler doesn't resolve `#lib`. `env.staging`, `env.beta` and `env.test` repeat every binding; a binding added at the top level must be added to all three. Cron strings in `wrangler.jsonc` must match the keys of `crons` exactly, or `runCron` throws.

### Data

For: The organization's records in D1 and files in R2.
Lives at: `migrations/0001_core.sql`, `src/lib/server/db/schema/`, `src/lib/server/db/index.ts`, `src/lib/server/storage.ts`, `src/lib/server/id.ts`
Seams: A module adds `schema/<module>.ts` (re-exported from `schema/index.ts`) and its reserved migration number. `search_index` (FTS5) is shared: each module keeps its rows current with triggers in its own migration.
Fragile: The SQL migration is the source of truth and the Drizzle schema mirrors it by hand; they drift silently. `org` has a single row with `id = 1`.

### Identity and access

For: Who is signed in, which role they hold (admin, member, viewer, guest), how people join (first-run setup, invites with starter projects, the email domain's join mode, join requests), onboarding after the first sign-in, and the org's own settings.
Lives at: `src/hooks.server.ts`, `src/lib/server/auth/`, `src/lib/server/setup.ts`, `src/lib/server/members.ts`, `src/lib/server/invites.ts`, `src/lib/server/join-requests.ts`, `src/lib/server/onboarding.ts`, `src/lib/server/org.ts`, `src/lib/server/dev-login.ts`, `migrations/0002_auth.sql`, `migrations/0012_auth2.sql`, `migrations/0023_invites2.sql`, routes `setup/`, `login/`, `logout/`, `auth/google/`, `invite/[token]/`, `onboarding/`, `members/`, `settings/`, `files/`
Seams: Routes call `requireMember(event, minRole)`; role order lives in `src/lib/roles.ts`. Every sign-in method (emailed link, Google) hands a vouched-for email to `signInFacts` + `completeSignIn`, and `decideSignIn` alone decides member, invitee, domain join, join request or refusal. Each of those that lets someone in, and the password form, ends in `finishSignIn` (`auth/finish.ts`), which starts a session, or the two-factor step at `/login/two-factor` when the user has it on; a join request ends on the sign-in page saying it was sent. Only `/dev/login` and accepting an invite (a new member, who can't have two-factor yet) create a session directly. `acceptInvite` puts the new member in the invite's starter projects (`joinStarterProjects`); a module that gives someone access to something else on joining adds its step there. `/files/<key>` serves R2 objects to signed-in members for the `avatars/`, `covers/`, `org/` and `emoji/` prefixes only; a module serving its own files adds its prefix and its access check there.
Fragile: The hook caches "org exists" per isolate once true. The hook also writes the signed-in person's theme into `<html>` by replacing `%theme%` in `src/app.html` (`transformPageChunk`), so the first paint is right with no script; removing the placeholder from `app.html` silently drops the saved theme until the page's script runs. `/dev/login` depends on `import.meta.env.DEV`, read per request. `locals.user` is read once per request, so a page whose action changes the user (profile) must reload from the database in its `load`, and the sidebar shows the old name until the next request. `/setup` redirects to `/login?setup=done` after it runs, because its own `load` answers 404 once the org exists. Deactivating a member deletes their sessions; `readSession` also refuses deactivated members, so both must stay. The last active admin can't be demoted or deactivated (`members.ts`). Wrong passwords and wrong two-factor codes are counted as rows in `sign_in_attempts` under `password:<email>` and `two-factor:<userId>`; changing a password in settings counts against the same `password:` key as the sign-in form. Each check writes its failure row before it runs (`takeFailureSlot`, one statement that counts and inserts, so concurrent requests can't all pass; null means the limit is reached and the caller refuses), and every caller must delete that row with `cancelFailure` when the answer is right, or a right answer counts as a failure. Sign-in-link, reset-link and invite requests are limited in the same table with the same one statement (`takeAttempt`, under `email:`, `ip:`, `reset:` and `reset-ip:`), and their rows are never taken back. An authenticator code is accepted once: `users.totp_last_step` is shared by turning two-factor on, signing in and the settings actions. A password reset deletes every session and closes the user's sockets, as deactivation does. A pending join request is a `users` row with no `members` row plus its `join_requests` row; denying deletes the user, which takes the request and the admins' notifications with it, and `createMember` reuses that user when a caller passes it as `existingUserId`: approving passes the request's user, and accepting an invite or joining directly passes `waitingRequester(email)`. Onboarding opens from Home only while `members.onboarding_step` is null and `onboarded_at` is unset, so a member created outside `createMember` (seeds, scripts) must set `onboarded_at` or they land in onboarding. The first admin is whoever has the oldest `members.created_at`. Admins answer join requests under Members (`/members?view=requests`, the path in their notifications and mail); Deny waits 5 seconds in the browser for an Undo before it posts, and leaving the page posts it at once, but a tab closed in those 5 seconds can drop it.

### People

For: Each member's username and profile page, status, local time, last seen, the hover card on a name, cover photos, the theme setting, and cropping an image before it's uploaded (avatar, cover, org logo, project cover).
Lives at: `migrations/0015_people.sql`, `src/lib/server/db/schema/people.ts` (and the new `users` columns in `core.ts`), `src/lib/server/people/` (`usernames.ts`, `status.ts`, `seen.ts`, `summary.ts`, `theme.ts`, `time-zone.ts`), `src/lib/people/` (browser-safe: status expiries, last-seen text, local time), `src/lib/components/people/`, `src/lib/components/images/` and `src/lib/images/crop.ts`, `src/lib/server/posts/project-cover.ts`, routes `people/[username]/`, `people/id/[userId]/` (and its `card/`), `settings/profile/` (and `theme/`), `settings/time-zone/`, `projects/[id]/cover/`
Why this shape: a profile's URL is `/people/<username>`; places that only know a user id link to `/people/id/<userId>`, which redirects. A renamed username keeps pointing at its person for 30 days (`username_redirects`), and nobody else can take it until then. Status lives on `users` and the `*/5` cron clears expired ones (`clearExpiredStatuses`). Last seen is written at most once a minute, from the hook on signed-in requests and from the realtime hub after a socket's message or close; a failed write there is logged and never fails the socket. A member's local time is written in `users.timezone`, which the root layout keeps in step with the browser: when the browser's zone moves, the layout posts to `settings/time-zone`, which saves it for a member who is still on the default UTC or on the browser's previous zone, and leaves a zone they chose in notification settings alone. Cropping happens in the browser (`renderCrop`); the server still checks type and size in `saveImage`.
Seams: New code finds a person by username with `lookUpUsername` and makes one with `availableUsername(env, suggestUsername(name))`. A project's cover is served by its own route, `projects/[id]/cover`, behind `loadProject`: who may see it is the project's rule, so it stays out of `/files/`.
Fragile: The username rule is written three times and must agree: `usernamePattern` in `usernames.ts`, the two triggers in 0015, and the `pattern` on the settings input (which also accepts capitals, since the server lowercases). `suggestUsername` must keep making what 0015's backfill made from a name (ASCII letters and digits, lowercased, cut to 27, else `member`), or people who join later get usernames by a different rule than everyone before them. Drizzle declares `users.username` `notNull()`, but the SQL column is nullable (SQLite can't add a NOT NULL column without a default); only the triggers refuse a missing one, so a migration that copies `users` forward must keep them. UTC in `users.timezone` means "never set", so a member who picks UTC by hand is moved to their browser's zone on their next visit. The rule for when the saved zone follows the browser is written twice and must agree: `zoneToFollow` in `src/lib/time-zone.ts` and the `WHERE` in `settings/time-zone/+server.ts`.

### Events, jobs and mail

For: Background work: domain events and outgoing email.
Lives at: `src/lib/server/events.ts`, `src/lib/server/jobs/index.ts`, `src/lib/server/email/index.ts`, `src/routes/__mail/`
Seams: `emit(env, event)` with a kind from `DomainEvent`; `sendEmail(env, msg)` with the transport chosen by `EMAIL_TRANSPORT`.
Fragile: Events with no handler are acked and logged `unhandled`, so a typo in a kind fails quietly. `/__mail` is reachable whenever `MAIL_VIEWER_TOKEN` is set.

### Projects and posts

For: Projects, posts, threaded comments, emoji reactions and file attachments, polls, checklists, server-side drafts and post versions, and the home and project feeds; feedback requests, reminders ("remind me") on posts, comments, notes and calls, link previews, and comments pinned to a point on an image; #tags and their tag pages, posts, notes and calls pinned to a project's top, a project's bookmarks, moving a post between projects, public links that show a post signed out, and the org's custom emoji with the emoji picker.
Lives at: `migrations/0003_posts.sql`, `migrations/0020_posts2.sql` (polls, drafts, versions), `migrations/0021_posts3.sql` (feedback requests, reminders, link previews, image comments; it also rebuilds `notifications`, see Notifications), `migrations/0022_posts4.sql` (tags, pins, bookmarks, moves, public links, custom emoji), `src/lib/server/db/schema/` (`posts.ts`, `feedback.ts`, `follow-ups.ts`, `link-previews.ts`, `posts4.ts`), `src/lib/server/posts/`, `src/lib/server/follow-ups.ts` (reminders and the cron that delivers them), `src/lib/server/link-previews.ts` (the fetch, its SSRF guard and the 24-hour cache), `src/lib/follow-ups.ts`, `src/lib/link-preview.ts`, `src/lib/emoji/` (the Unicode emoji data, loaded only when the picker opens, and the picker's search, skin tone and frequently used), `src/lib/components/posts/`, `src/lib/components/editor/LinkPreview.svelte`, `src/routes/projects/`, `src/routes/posts/`, `src/routes/drafts/`, `src/routes/follow-ups/` (the Reminders page and the reminder actions every subject's page posts to), `src/routes/link-preview/` (previews, and YouTube thumbnails passed on so the browser never calls YouTube before play), `src/routes/files/attachments/`, `src/routes/tags/` (a tag's posts in the projects the reader can see), `src/routes/p/` (a public post, its files and the org logo, signed out), `src/routes/settings/emoji/` (adding and removing custom emoji), `src/routes/+page.*` (home feed)
Seams: Who may see or write in a project is `canSeeProject` / `canWriteInProject` in `src/lib/server/posts/access.ts`; SQL that lists projects filters with `visibleProjectIds(who)`. Other modules that attach content to a project (search, notes, chat) go through these. Posts emit `post.created`, `post.updated`, `comment.created`, `reaction.created`, `mention`, `feedback.requested` and `post.moved`, and projects emit `project.member_added`, `project.renamed` and `project.archived`; they publish to `project:<id>` and `post:<id>`. The composer (`PostComposer.svelte`) autosaves to `POST /drafts` then `PUT /drafts/<id>` after 2 s without typing, and moves the URL to `/drafts/<id>`; both its pages publish with `publishPost`, which creates the post and deletes the draft. A page that renders post or comment bodies and wants checkboxes live implements a `?/tick` action (`tickTask` for posts, `tickNoteComment` for note comments); `submitTick` calls it. A public link (`loadPublicPost` in `public-links.ts`) serves the post's title, body, author name and date, and the files its body shows, to anyone holding the token, signed out, while the org has public links on; mention ids are dropped from the body first.
Fragile: People are referenced by `users.id` everywhere in this module, not `members.id`. `reactions.subject_id` has no foreign key; triggers in 0003 delete reactions with their post or comment. `search_index` rows for posts and comments are kept by triggers, with visibility `project` meaning whoever can see `project_id`. Attachments in a project are readable by anyone who can see the project, whether or not a post links them yet. `follow_ups.subject_id` has no foreign key, because a reminder's subject is a post, comment, note or call; four triggers in 0021 (`posts_delete_follow_ups`, `comments_delete_follow_ups`, `notes_delete_follow_ups`, `calls_delete_follow_ups`) delete reminders with their subject, so a new subject type needs its own. `post_feedback_requests.replied_at` is written only by the `comments_feedback_replied` trigger, on the asked person's first comment on the post; no app code sets it. The link-preview guard refuses hosts that are private as written and doesn't resolve names: a public name that resolves to a private address is left to Workers' outbound fetch, which can't reach a private network. Drafts live in `post_drafts`, never in `posts`, which is what keeps them out of feeds, search and notifications. A version is a post whose `parent_id` is the version before it; `feed` shows only posts nothing points at, so a query that lists posts some other way shows every version. A trigger in 0020 relinks the chain when a middle version is deleted. `movePost` moves the whole chain, because anyone who can see a version's project can read it. A tick rewrites the whole body it read, so two ticks on the same body at the same instant can lose one. Who may tick or vote is whoever may write in the project (`canWriteInProject`), and a note comment's tick follows `canDiscussNote`. `project_pins.subject_id` has no foreign key, because a pin's subject is a post, note or call; the triggers in 0022 (`posts_delete_pins`, `notes_delete_pins`, `calls_delete_pins`) and `movePost`, which drops the pins on every version it moves, are the only things that remove a pin, so a new subject type or another way of moving content needs its own. `post_tags` is kept in step only by `saveTags`, which `createPost` and `updatePost` call; anything else that writes a post's body leaves its tags stale. The public post page serves a body's images and attachments through `/p/<token>/files/<id>`, working the id out of the `/files/attachments/<id>` path the editor stores (`attachmentPath`, read back by `attachmentIdOf`); a change to that path breaks the public page's files. `emoji/` is in `/files`' `memberVisible`, so every custom emoji image is readable by any signed-in member, guests included. A pin and a public link point at one version's row: a new version is neither pinned nor shared until someone pins or shares it, and the older version keeps its pin and its link.

### Notes

For: Long-form notes, private to their author until shared with people or a project, edited live by everyone with edit access, with comments and reactions.
Lives at: `migrations/0004_notes.sql`, `migrations/0024_parity.sql`, `src/lib/server/db/schema/notes.ts`, `src/lib/server/notes/`, `src/lib/server/realtime/note-room.ts`, `src/lib/notes/` (`live.ts` protocol constants, `connection.ts` the browser's connection), `src/lib/components/notes/`, `src/routes/notes/`, `src/routes/p/notes/`, `src/lib/notes-nav.ts`, `tests/e2e/`
Why this shape: a note's body is a Yjs document held by the `RealtimeHub` instance named `note:<id>` (`NoteRoom`). The browser connects at `/realtime/note/<id>`; the Worker checks the session and `noteAccess` and tells the hub whether the socket may write. Frames are y-protocols sync and awareness, binary. The hub stores every change in its own SQLite before relaying it; after `idleMs` without changes (an alarm) and when the last socket closes it writes the document to R2 (`notes/<id>/ydoc.bin`), the derived body to the D1 row (`saveLiveBody`: body, body_text, version + 1, updated_by), and compacts its rows. The D1 row is a copy for search, summaries, lists and the first paint, never written by the editor directly.
Seams: Who may see or edit a note is `noteAccess(noteFacts(...))` in `src/lib/server/notes/access.ts`; SQL that lists notes filters with `visibleNoteIds(who)`, and search should too. A project share goes through `canSeeProject`, so a guest reaches a project's notes only once added to the project. Titles are plain fields renamed with `renameNote` (last rename wins). Sharing with a person emits `note.shared`; mentions emit `mention` with subject `note`, only for people who can see the note, when a snapshot finds them newly in the body. A note's author and everyone who comments on it are in `note_subscriptions`; each new comment emits `note.commented`, whose handler tells the subscribers who can still see the note, leaving out its writer and the people it mentions, and deleting the comment takes those notifications back (`deleteWithNotifications`, `{ noteComment }`). Notes publish comments, reactions, renames and sharing to `note:<id>` on the org hub. Changing a note's sharing calls `closeLiveNote` (sockets reconnect and are checked again); deleting it calls `deleteLiveNote` (sockets closed, hub storage and R2 snapshot removed). The pages reuse the posts' `CommentThread`, `CommentForm` and `Reactions`, whose form actions (`?/comment`, `?/editComment`, `?/deleteComment`, `?/react`) the note page implements under the same names; `CommentThread`'s `threadResolution` adds a note's own `?/resolveComment` and `?/unresolveComment`, open to anyone who can see the note. A comment made on words in the note is a `noteComment` mark in the live document carrying only the comment's id: `?/comment` takes the words' ends as Yjs relative positions the browser encoded from its copy (`anchorStart`, `anchorEnd`), creates the comment, then asks the note's hub to mark the text between them (`markLiveComment`, the hub's internal `/note/mark-comment`, `comment-marks.ts`), so anyone who may comment can, on a read-only socket too, and the mark moves with concurrent edits like any text; deleting the thread takes its mark off (`/note/unmark-comment`), deleting the words leaves the comment unanchored in the list, and the public page drops the marks. Anyone with edit access publishes a note to the web (`setNotePublic` in `src/lib/server/notes/public.ts`, `?/publish`): it sets `notes.public_token` from `randomToken()` and `/p/notes/<token>` renders the stored D1 body signed out, with the ids of mentioned people, notes, posts and calls dropped (`withoutMentionIds`, `withoutResourceIds`) and the posts' `PublicFrame` and dead-link page; the org's `publicPosts` switch governs posts and notes alike. Resting on or focusing a link to a note (its path, as `linkedNoteId` reads it) in a rendered body or the note editor shows `NoteLinkCard`, filled from `GET /notes/<id>/card` (title, author, last update, thumbnail version; `loadNote`'s 404 for anyone who can't open it, which shows no card at all); the public pages turn it off (`noteCards={false}`).
Fragile: Note comments and reactions live in `note_comments` and `note_reactions`, not the posts' tables, and emit `note.commented`, never `comment.created`, whose consumers read `comments`. `search_index` rows for notes have visibility `note`, which only `visibleNoteIds` can resolve. Files uploaded into a note (`POST /notes/<id>/attachments`, open to anyone with edit access) live in `note_attachments`, not `attachments`, whose rows belong to a project or a thread; their bytes share the R2 scheme `attachments/<id>`. A web image in Markdown pasted into a note is fetched into it the same way (`POST /notes/<id>/attachments/from-url`, `importNoteImage`): the server fetches it through the link previews' guard (`fetchPublicResponse`: no private hosts, each redirect checked) with a time limit and stores it as an upload, so an image type and the size limit apply; the editor inserts the paste only once its images are in, at the selection held as Yjs relative positions, and one that fails stays a link. `readAttachment` falls back to `note_attachments`, so `/files/attachments/<id>` serves a note's file to anyone `loadNote` lets open the note, whether or not its body still shows it, and 404s everyone else. A public note serves a file at `/p/notes/<token>/files/<id>` only while its D1 body shows it and the file was uploaded into that note (`publicNoteFile`), `no-store` like a public post's files. A comment pinned to a note's image (`pinNoteComment`) names a `note_attachments` row of the same note, which must be an image. A note's hub seeds its document from the D1 body only when it has no rows and R2 has no snapshot; seeding twice would duplicate the text when the two documents merge, so neither the hub's storage nor the R2 object may be removed while the note exists. A socket's access is checked when it connects and again at its first frame after `recheckMs`; sharing changes close the note's sockets at once, other changes (project membership, roles, deactivation) take effect within that interval. A body holding a node `sanitizeDoc` refuses is kept in the live document and R2 but not written to D1 (logged by `saveLiveBody`). The hub trusts its upgrade headers (`x-campfire-user-id`, and `x-campfire-note-socket`, whose presence makes a socket a note socket), so `connectRealtime` builds the forwarded headers from scratch and never copies the browser's. Its other routes (`/publish`, `/note/close`, `/note/delete`, `/note/mark-comment`, `/note/unmark-comment`) trust their callers just as much: only Worker code reaches them, through the stub, because `connectRealtime` forwards nothing but WebSocket upgrades, which `RealtimeHub.fetch` takes before any route. A comment mark is written under the key y-prosemirror gives overlapping marks, a hash of the mark (`commentMarkKey`, the same as `marksToAttributes` in `@tiptap/y-tiptap`); if that hash ever changes, editors would rewrite the marks already there. The hub marks a passage as a change of the commenter's, so a viewer who comments can be a snapshot's `updated_by`. A note's snapshot and its delete run one at a time (`NoteRoom.inTurn`), so a delete never lands between a snapshot's R2 write and its compaction. A public note page is sent with `max-age=60` (`public` signed out, `private` to a member, whose page carries their layout data), so an edit or a Disable can take a minute to show; its 404 is `no-store`. Disable clears the token, so publishing again makes a new URL and the old one stays dead. Each signed-out request to it adds one to `notes.anonymous_views`, cached copies excepted, so the count is a floor. `note_events.ref_id` has no foreign key, because a reference comes from a post or a note; the triggers `posts_delete_note_events` and `notes_delete_note_references` in 0024 delete a note's `referenced` lines with the post or note that made them, so a new kind of referencing item needs its own. A note's thumbnails (`notes/<id>/thumb-<version>.png` and `-grid.png`) are drawn inside the Worker by `renderNoteThumbnails` (`notes/thumbnail.ts`: Satori and resvg as WebAssembly, Inter as .woff) in the `note.thumbnail` job that `saveLiveBody` and `renameNote` emit (each bumps `version`); only `jobs/index.ts` may import that module, because wrangler's module rules (`.wasm` by default, `.woff` in `wrangler.jsonc`) load its files and Vite can't, so a page importing it breaks the build. Pages use `notes/thumbnails.ts`, which imports only its types; under Vitest an alias in `vite.config.ts` reads the files from disk. Deleting a note's hub deletes everything under `notes/<id>/` in R2, thumbnails included. `thumbnail.ts` copies four light-theme colours from `tokens.css` as literal values, because Satori needs concrete ones and resvg can't read `oklch()`; a change to those tokens has to be made there too, and a thumbnail already drawn keeps the old ones until its note next changes.

### Editor

For: The rich-text editor and the read-only renderer for its documents, shared by posts, comments, notes (live) and chat (compact).
Lives at: `src/lib/components/editor/`, `src/lib/editor/doc.ts`, `src/lib/editor/extensions.ts`, `src/lib/editor/slash.ts`, `src/lib/editor/suggestion-popup.ts`, `src/routes/mentions/`
Seams: Bodies are ProseMirror JSON. `sanitizeDoc` (server) is the allowlist of nodes, marks and attributes; `RichText.svelte` renders exactly that set without `{@html}`. `documentExtensions` in `src/lib/editor/extensions.ts` defines the nodes and marks, with no DOM or Svelte, so the server builds the same schema (`documentSchema`) to seed live notes. Adding a node means adding it to `documentExtensions`, `sanitizeDoc` and `RichText` together. ### Call recordings

For: Recording a call: each person's audio server-side, the call's video from the browser that pressed Record, speaker-labelled transcripts, and the call's title and summary sections written from all its recordings' transcripts once the call ends; plus the hourly check that fails stuck recordings.
Lives at: `migrations/0013_recordings.sql`, `src/lib/server/db/schema/recordings.ts`, `src/lib/server/recordings/` (`recordings.ts` start, stop and the SFU adapters; `sink.ts` the sink route and the `RecordingSink` Durable Object; `transcripts.ts` Whisper, the summary and the job handlers; `video.ts` the multipart upload; `view.ts` what the call page reads; `health.ts`), `src/lib/calls/audio.ts` (packets, resampling, WAV, segments, the playback mix; no runtime dependency, shared with the browser), `src/lib/calls/video-recorder.ts`, `src/lib/components/calls/RecordingBar.svelte` and `RecordingList.svelte`, routes `calls/[id]/recordings/` (start and stop, video, audio segments), the `/calls/<id>/rec-sink` branch in `src/worker.ts`, `tests/e2e/recordings.spec.ts`
Why this shape: Realtime's SFU records nothing itself. On Record the Worker asks it for one WebSocket adapter per published microphone (`/adapters/websocket/new`, egress as 48 kHz stereo PCM) pointed at `/calls/<id>/rec-sink?track=…&token=…`; the Worker checks the token and hands the socket to the track's `RecordingSink` (`idFromName(trackId)`), which turns packets into 16 kHz mono and writes a WAV segment to R2 each minute (`calls/<callId>/rec/<recordingId>/<participantId>/<seq>.wav`), then queues `recording.segment`. Each segment goes to Whisper and becomes timed lines, the speaker being the track's participant. A stopped recording is ready once `flushGraceMs` has passed and no segment is pending. Once the call has ended and none of its recordings is still recording or processing, `summarizeCallIfDone` runs `groundedSummary` over every recording's lines, in the order the recordings ran, and writes the summary, topics and next-steps sections to the call, each bullet citing lines, with `groundedTitle`'s title (none when no title passes). It runs on `call.ended`, after each recording job, and when the hourly check fails a stuck recording, so whichever comes last writes it. The hourly check also stops a recording that has run `maxRecordingMs` (4 h), or whose call ended without stopping it. The video is a canvas of the call's tiles plus the mixed audio, recorded with MediaRecorder and uploaded in parts of 5 MiB or more. An upload completed with no parts is dropped and the recording keeps no video; the video route answers a Range from the object's size itself, 416 past the end, since R2 failed such a range with a 500.
Seams: The calls module calls `syncRecording` whenever who publishes a microphone changes (publishing, leaving, a participant found gone) and `endRecording` when the call ends. Who may start or stop a recording is `canRecord`: whoever may post in the call's place (`canWriteInProject`, a thread's members, a room's owner and members). Recording is offered only when `recordingAvailable` (calls, the AI binding, `APP_URL` and `SESSION_SECRET`). Who may see a recording, its media and its transcript is whoever can see the call (`loadCall`); only the person who started it uploads its video.
Fragile: The sink token is an HMAC of the recording id under `SESSION_SECRET`, so changing that secret refuses every running recording's sinks. It must never reach a browser or a log: the SFU client redacts `token=` in its errors, and the sink route forwards a fresh request without the URL. A track row is written before its adapter is asked for, so the sink route knows the track when the SFU connects; a closed track refuses the SFU's reconnects. A sink holds the minute in progress in memory (the socket is not hibernated); if its instance is evicted mid-minute that audio is lost, and a new instance numbers its segments after the last saved one. Time in a segment follows when packets arrive: a gap up to 2 s is filled with silence, a longer one starts a new segment, and a segment of pure silence is dropped. A segment written more than `flushGraceMs` after the stop is transcribed but may miss the summary. The playback mix holds the whole recording's audio in the browser's memory. Transcripts longer than the summary model's context fail the summary job; after the queue's retries the call has no title or summary, and its recordings and transcripts stay readable.

### Cal.com

For: Giving meetings booked on Cal.com a call here: each member's connection page, the admin's off switch, each member's webhook, and the booking's join link, for members and for outside attendees as guests.
Lives at: `src/lib/server/calcom/calcom.ts`, `src/lib/server/calcom/guests.ts`, `migrations/0010_calcom.sql`, `migrations/0014_calcom2.sql`, `src/lib/server/db/schema/calcom.ts`, routes `settings/calcom/`, `integrations/calcom/webhook/[id]/`, `calls/booking/[id]/` (member redirect and guest lobby), `calls/[id]/guest/`, the booking block on `calls/[id]/`, and the switch on `settings/org/`
Why this shape: Cal.com calls out only through webhooks and its API, so a booking arrives on the webhook (checked against `x-cal-signature-256`) and is stored in `calcom_bookings`; each member has one row in `calcom_connections` (their webhook id, secret, API key and place), and a booking belongs to the member whose webhook received it (`calcom_bookings.owner_id`). Its link, `/calls/booking/<id>?guest=<signature>`, is written onto the Cal.com booking with the owner's API key; Cal.com shows one location to everyone on a booking, so the signature is per booking, an HMAC over its id. A call exists only while it's live, so the link starts or joins the live call in the owner's chosen place when someone opens it, and tags that call with `calls.calcom_booking_id`. Someone not signed in, with a valid signature, gets a lobby listing the attendees who aren't active members; joining as one issues a guest pass for the booking's window.
Seams: `calcomAvailable(env)` (calls on and `SESSION_SECRET` set) and `org.calcom_enabled` together make `calcomOn(env)`, which the webhook, the settings page and the booking link check; a guest already holding a pass keeps it. `openBookingCall` and `joinAsGuest` go through `startCall`, so who may join is the calls module's `canSeePlace` on the owner's place; a guest's call is started as the owner. `bookingOfCall` is what the call page shows.
Fragile: The webhook secret and API key are encrypted under a key derived from `SESSION_SECRET`; changing that secret makes them unreadable, and every Cal.com page and delivery then fails until the `calcom_connections` rows are deleted by hand (README); guest links are signed under another key derived from it, so they stop working too. The place is read when a link is opened, not when the booking arrives, so a member who changes their place moves the calls of bookings already made. Opening a booking's link while another call is live in the chosen project joins that call, which takes the booking's tag only if it had none. The webhook writes the booking before it calls Cal.com's API, so a failed location update leaves a stored booking that Cal.com's retry finds again.

### App shell

For: The signed-in frame: sidebar navigation, org name, current user, and the global keyboard shortcuts with the sheet that lists them on `?`. Also the installed app: its manifest and icons, the offline page, the install prompt and the app icon's unread badge.
Lives at: `src/routes/+layout.svelte`, `src/routes/+layout.server.ts`, `src/lib/components/shell/`, `src/lib/nav.ts`, `src/lib/keyboard.ts` (whether a key was typed into a field), `src/lib/strings/`; the installed app in `src/routes/manifest.webmanifest/`, `src/routes/offline/`, `src/service-worker/index.ts`, `src/lib/install-prompt.svelte.ts`, `src/lib/pwa.ts`, `src/lib/assets/mark.svg` and `mark-maskable.svg`, and `static/icons/`
Seams: Modules append sidebar items with `addNav()` and add `src/lib/strings/<module>.ts`.
Fragile: `nav.ts` items appear only if the module file that calls `addNav()` is imported somewhere on the page's path. The manifest and the theme-color tags carry the page background as hex (`src/lib/pwa.ts`), and `pwa.svelte.test.ts` fails when `--hue-z0-bg` moves away from it. The mark SVGs (`src/lib/assets/mark.svg`, `mark-maskable.svg`) carry `--hue-gray-900`, `--hue-orange-500` and `--hue-amber-300` as hex, in that order, because librsvg can't read oklch, and the same test fails when a fill no longer paints as its token. The PNGs in `static/icons/` are rendered from the mark SVGs by `scripts/app-icons.sh`: edit the SVG, then run it. The service worker caches only the offline page and the build's stylesheets, per build version; the page is fetched with no cookies, so it must stay a page that renders signed out.
